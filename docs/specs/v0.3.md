# Spec sjck-graph v0.3 — misura, watchdog, findings, critico

Questa spec è l'input di un run `/sjck-run` in modalità L. È scritta per
essere scomposta: le sezioni A–F sono componenti con file quasi disgiunti.
Ogni componente ha criteri di accettazione verificabili.

## Vincoli globali
- Repo: `sjck`. Tutto il codice del plugin sta in `sjck-graph/`.
- Script: Python 3.9+, **solo standard library**. Niente dipendenze.
- Gli hook non devono MAI rompere Claude Code: ogni errore interno → exit 0
  silenzioso, salvo i blocchi intenzionali del watchdog.
- Compatibilità: un `state.json` della v0.2 deve restare leggibile
  (campi nuovi opzionali, con default).
- Prima di usare un campo di hook o di frontmatter, verificalo sulla
  documentazione ufficiale: https://code.claude.com/docs/en/hooks e
  https://code.claude.com/docs/en/subagents. Se un dato non è disponibile
  (es. quale subagente ha fatto la tool call), degrada in modo esplicito e
  documentalo in `sjck-graph/docs/limitations.md`.
- Tutti i test in `sjck-graph/tests/`, eseguibili con
  `python3 -m unittest discover -s sjck-graph/tests`.
- Aggiorna `CHANGELOG.md` (sezione 0.3.0), `README.md` e la versione in
  `sjck-graph/.claude-plugin/plugin.json` → `0.3.0`. Questo lo fa UN solo nodo
  finale, non i nodi paralleli.

## A. Metriche di piano e di contesto
File: `sjck-graph/scripts/plan_score.py`, test.
- `score(state, cards_dir) -> plan_score` calcola: larghezza massima del DAG
  (nodi per livello topologico), percorso critico (lunghezza in nodi),
  sovrapposizione di `files` tra nodi che possono girare in parallelo,
  token stimati per card (`len(text)/4`), cicli.
- `verdict: reject` se: ciclo, `file_overlap > 0`, una card supera
  `budget.context_tokens`, oppure un nodo ha 0 criteri di accettazione.
- CLI: `python3 plan_score.py --cwd DIR` scrive `plan_score` nello stato.
Criteri:
- [ ] Test su 4 DAG di esempio: lineare, largo, con overlap, con ciclo.
- [ ] La skill chiama lo score dopo il piano e NON parte se `reject`.

## B. Watchdog (hook)
File: `sjck-graph/scripts/watchdog.py`, voci in `sjck-graph/hooks/hooks.json`, test.
Rileva, per nodo `running`:
1. **loop**: stesso comando Bash (normalizzato) o stesso output d'errore
   ripetuto ≥3 volte; stesso file modificato e riportato allo stato precedente.
2. **deriva**: scrittura fuori da "Puoi modificare" della card; letture fuori
   da "Leggi" (contate, non bloccate).
3. **budget**: tool call oltre `budget.tool_calls`.
Escalation:
- livello 1 → messaggio di richiamo all'agente (obiettivo della card + il
  pattern rilevato + "se non riguarda l'obiettivo, annotalo in findings e
  prosegui");
- livello 2 (pattern ripetuto dopo il richiamo, o budget superato del 25%) →
  blocca le tool call successive tranne la scrittura di `.sjck/out/<ID>.json`
  e `.sjck/findings.jsonl`, istruendo l'agente a chiudere con
  `status: blocked` e la descrizione del problema;
- livello 3 è dell'orchestratore (vedi skill).
Tutto aggiorna `usage` del nodo e scrive eventi in `.sjck/watchdog.jsonl`.
Le scritture fuori card vengono bloccate già al livello 1 (PreToolUse).
Criteri:
- [ ] Test con sequenze sintetiche di input hook per ciascun pattern.
- [ ] Nessun falso positivo sui file `.sjck/**`.
- [ ] Senza `state.json` o senza nodi `running`, l'hook non fa nulla.
- [ ] Tempo di esecuzione < 100 ms per chiamata (misurato nei test).

## C. Findings
File: `sjck-graph/scripts/findings.py`, aggiornamenti agli agenti, test.
- Formato `.sjck/findings.jsonl`: `id, from, file, kind
  (bug|smell|debt|doc|loop), severity (high|med|low), what, suggested_fix,
  status (open|proposed|accepted|deferred|rejected), placement`.
- CLI `findings.py add ...` (usata dagli agenti, assegna l'id) e
  `findings.py dedupe` (stesso file ±5 righe + testo simile → unisce).
- Tutti gli agenti: regola "non sistemare ciò che è fuori scope: aggiungilo ai
  findings". Card con nuova sezione `## Fuori scope`.
- Il JSON di output degli agenti guadagna `assumptions: []` (regola "decidi e
  annota" per le scelte con default ragionevole).
Criteri:
- [ ] Test di add/dedupe/transizioni di stato.
- [ ] Gli agenti aggiornati citano la CLI con il percorso corretto sia in
      modalità plugin (`${CLAUDE_PLUGIN_ROOT}`) sia con install.sh.

## D. Critico
File: `sjck-graph/agents/critic.md`, aggiornamento della skill.
- Agente read-only, default `model: fable`, `effort: high` (diverso
  dall'orchestratore). Riceve SOLO: la proposta, lo `plan_score` o i findings
  in questione, e il goal. Mai il codice.
- Interviene in 3 punti: piano iniziale (solo modalità L), posizionamento dei
  findings accettati, gestione di un nodo `failed`.
- Risponde `{"verdict":"approve|object","points":[...],"alternative":"..."}`.
- Protocollo: max 2 round; poi disaccordo → all'utente con le due posizioni
  in max 3 righe ciascuna. Tutto registrato in `state.critic`.
Criteri:
- [ ] La skill descrive il protocollo e i 3 punti d'intervento.
- [ ] Il critico ha solo tool Read/Grep e un `maxTurns` basso.

## E. Modello ed effort per nodo + skill aggiornata
File: `sjck-graph/skills/sjck-orchestration/SKILL.md`, frontmatter degli agenti.
- Frontmatter di default: planner opus/high, scout haiku/low,
  implementer sonnet/medium, validator sonnet/high, reviewer opus/high,
  critic fable/high. Aggiungi `maxTurns` sensati a scout, implementer,
  validator, critic, e `omitClaudeMd: true` a scout e implementer.
- Il planner assegna `model`, `effort`, `budget` per nodo con una regola
  scritta (difficoltà, rischio, file toccati); l'orchestratore li passa
  come override al lancio.
- La skill integra: plan score (A), escalation livello 3 del watchdog
  (rimanda come nuovo nodo / rispondi nella card / ripianifica), checkpoint
  dei findings a fine di ogni livello del DAG con proposta di posizionamento e
  approvazione dell'utente via domanda a scelta multipla (eccezione: `high`
  che blocca nodi pianificati → subito), critico (D), backlog in
  `.sjck/backlog.md` per i rimandati.
Criteri:
- [ ] Skill ≤ ~180 righe: se cresce, sposta i dettagli in
      `sjck-graph/skills/sjck-orchestration/reference/*.md` citati dalla skill.
- [ ] Nessuna regola della v0.2 persa (verifica con un diff ragionato).

## F. Eval harness
File: `evals/` nella root del repo, `sjck-graph/commands/sjck-eval.md`.
- `evals/tasks/<id>/`: ogni task ha `task.md` (prompt), `repo/` (fixture
  minima, autonoma, senza ROS installato), `check.sh` (exit 0 = successo),
  `meta.json` (`size: S|M|L`, tag).
- 6 task ispirate a uno stack di robotica ROS 2 ma in Python puro:
  2 S (es. fix di un bug in un parser di parametri YAML), 2 M (es. aggiungere
  un servizio a un nodo mock con test), 2 L (es. un modulo con 3 parti
  indipendenti: messaggi, nodo, test d'integrazione). Almeno una task deve
  contenere un "rabbit hole" volontario (warning irrilevante) per testare il
  watchdog, e una un bug fuori scope per testare i findings.
- `evals/run.py`: per ogni task copia la fixture in una dir temporanea, lancia
  `claude -p "/sjck-run <task.md>"` (comando e flag configurabili),
  esegue `check.sh`, raccoglie `metrics` e `plan_score` dallo stato e scrive
  `evals/results/<timestamp>.json`.
- `evals/compare.py A.json B.json` → tabella: successo, tool call, durata,
  validator_fails, watchdog, findings per task e totali.
- `--dry-run` che valida le fixture senza lanciare Claude (usato nei test).
Criteri:
- [ ] `python3 evals/run.py --dry-run` passa: ogni `check.sh` fallisce sulla
      fixture originale (la task non è già risolta).
- [ ] `compare.py` testato su due risultati sintetici.
