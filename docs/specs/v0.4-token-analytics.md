# Spec graph-kit v0.4 — token analytics

Obiettivo: sapere con DATI REALI dove vanno i token di un run e dove il kit li
risparmia davvero (o li spreca). Si costruisce DOPO la v0.3: usa lo schema di
stato, l'eval harness e il visualizzatore della v0.3.

## Vincoli
- Python 3.9+, solo standard library. Nessuna chiamata di rete.
- I numeri vengono dai transcript reali di Claude Code, non da stime.
  Le stime (`len/4`) sono ammesse solo dove il dato reale non esiste, e vanno
  marcate `estimated: true`.
- Prima di scrivere il parser, ispeziona transcript reali e verifica il
  formato sulla documentazione ufficiale (https://code.claude.com/docs).
  Il formato non è un contratto stabile: il parser deve ignorare i campi
  sconosciuti, non rompersi su righe malformate, e avere test su fixture
  anonimizzate prese da transcript veri (senza contenuto, solo struttura).
- Privacy: i report contengono numeri, nomi di tool e percorsi di file, MAI il
  testo dei messaggi o il contenuto dei file.

## A. Raccolta
File: `graph-kit/scripts/tokens/collect.py`, test.
- Fonti: il transcript della sessione principale (percorso dall'input degli
  hook, `transcript_path`) e i transcript dei subagenti del run.
  Collega ogni subagente al suo nodo tramite `agent_id` in state.json; se il
  collegamento non è possibile, attribuisci a `unattributed` e documentalo.
- Per ogni turno API estrai: input, output, cache_read, cache_creation,
  modello, timestamp.
- Per ogni turno attribuisci l'input a categorie, usando i blocchi del turno
  precedente:
  `system` (prompt di sistema + definizioni agente + CLAUDE.md),
  `card` (lettura di .graph/cards/*), `interfaces` (.graph/interfaces/*),
  `file_read_in_card`, `file_read_outside_card`, `tool_output_bash`,
  `tool_output_other`, `agent_messages` (risultati dei subagenti nel contesto
  dell'orchestratore), `user`, `own_output` (output precedenti che restano in
  contesto).
- Output: `.graph/tokens.json` con totali per run, per nodo, per agente, per
  modello e per categoria, più la serie temporale cumulativa.
- Aggiornato a fine di ogni nodo (hook `SubagentStop`, se disponibile) e a fine
  run. Mai durante ogni tool call: costerebbe troppo tempo.
Criteri:
- [ ] Test su fixture: somme per categoria = totale del turno (± arrotondamenti).
- [ ] Un run senza subagenti (modalità S) produce comunque un report valido.

## B. Costo
File: `graph-kit/scripts/tokens/cost.py`, `graph-kit/scripts/tokens/prices.json`.
- Prezzi per modello e per tipo di token (input, output, cache read,
  cache write) in un file modificabile dall'utente, con data di aggiornamento.
  Il kit non deve inventare prezzi: se un modello manca, mostra solo i token.
- Converte `tokens.json` in costo per nodo/agente/categoria.

## C. Dove si risparmia (analisi)
File: `graph-kit/scripts/tokens/analyze.py`, test.
Calcola e spiega in linguaggio semplice:
1. **Cache**: hit rate (`cache_read / input totale`) per agente; segnala i
   subagenti che non riusano la cache.
2. **Contesto dell'orchestratore**: quanto cresce per nodo. Confronta i token
   dei JSON di output dei subagenti con quelli che sarebbero entrati se
   l'orchestratore avesse letto lui i file modificati (stima dai file in
   `changed`). Questo è il risparmio "da contract".
3. **Card vs esplorazione**: per ogni nodo, quota di input da card/interfacce
   vs letture fuori card. Letture fuori card alte = card povere.
4. **Spreco**: token spesi in nodi poi falliti, in tentativi ripetuti, in
   loop fermati dal watchdog, in nodi `blocked`.
5. **Scelta del modello**: token spesi con opus su nodi che il validator ha
   approvato al primo colpo e che hanno toccato ≤2 file (candidati a sonnet),
   e viceversa nodi con haiku/sonnet falliti più volte.
6. **Top 5 consumatori**: i turni/tool output più costosi del run, con
   categoria e nodo.
Output: `.graph/token-report.json` con una lista di `insights`, ciascuno con
`{kind, node, tokens, saving_estimate, suggestion}`.

## D. Baseline: il risparmio vero si misura solo contro un'alternativa
Estende l'eval harness della v0.3.
- `evals/run.py --baseline`: esegue la stessa task in modalità "agente
  singolo, senza kit" (comando configurabile, es. `claude -p "<task.md>"`
  senza /run-graph) e raccoglie gli stessi dati dal transcript.
- `evals/compare.py` aggiunge le colonne: token totali, costo, token per
  task riuscita, durata, per kit vs baseline e per versione vs versione.
- Regola: un risparmio si dichiara solo se la task è riuscita in entrambe le
  modalità. Kit più economico ma task fallita = non è un risparmio.
Criteri:
- [ ] `--dry-run` copre anche la modalità baseline.
- [ ] `compare.py` testato con risultati sintetici (kit vince, perde, pareggia,
      una delle due fallisce).

## E. Token visualizer
File: `graph-kit/scripts/tokens/view.py`, `graph-kit/commands/graph-tokens.md`.
Genera `.graph/tokens.html` (autonomo, stesso stile e tema chiaro/scuro di
view.html; grafici in SVG generato dallo script, nessuna libreria esterna):
- KPI in alto: token totali, costo, cache hit rate, token per nodo validato.
- Barre impilate per nodo, colorate per categoria (sezione A).
- Ripartizione per agente e per modello.
- Curva cumulativa nel tempo con marcatori sugli eventi (nodo validato,
  fail, stop del watchdog).
- Pannello "Dove si risparmia / si spreca" con gli insights della sezione C.
- Se esiste un confronto con baseline o versione precedente: affiancati.
Il visualizzatore del grafo (view.html) mostra per ogni nodo i token e un link
a tokens.html.
Comando `/graph-tokens`: rigenera i dati e apre la pagina; con `--archive`
mostra l'andamento sugli ultimi N run archiviati.
Criteri:
- [ ] Funziona con un report vuoto, con un run S e con un run L (test).
- [ ] Leggibile a larghezza telefono, senza scroll orizzontale.
